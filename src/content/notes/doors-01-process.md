> 按 16 个阶段组织的实践笔记：每个阶段讲清 **在干什么 → 用什么工具 → 工具边界 → PM 边界 → 优缺点 → 常见坑**。
> 阶段划分与能力域图左侧一列严格对应。

---

## 总览

### 0.1 需求的一生

```
需求获取 → 需求分析 → 需求规格化 → 需求评审 → 需求基线
   → 架构设计 → 详细设计 → 需求分配 → 编码实现
   → 单元测试 → 集成测试 → 系统测试 → 验收测试
   → 发布上线 → 变更控制 → 追溯与度量
```

### 0.2 三条铁律

| 铁律 | 含义 | 违反的后果 |
|---|---|---|
| 唯一主责 | 每个阶段有且只有一个工具/角色负责 | 责任真空，出问题互相甩锅 |
| 双向可追溯 | 任一需求能查到“从哪来、到哪去” | 变更漏改，测试漏测 |
| 变更受控 | 改需求必须走流程、留痕迹 | 版本混乱，交付对不上 |

这三条不是流程规定，而是**失效模式的反面**：没有唯一主责，出了问题就互相甩锅；没有双向追溯，改一处就漏三处；没有变更受控，交付的版本永远说不清。任何一条缺失，工具再贵也救不回来。

### 0.3 16 阶段速查表

| # | 阶段 | 核心问题 | 主责工具 |
|---|---|---|---|
| 1 | 需求获取 | 谁、在什么场景、想要什么 | Jira / Confluence |
| 2 | 需求分析 | 哪些做、先做哪个、冲突怎么解 | Jira |
| 3 | 需求规格化 | 怎么写成可验证、可追溯的需求 | DOORS |
| 4 | 需求评审 | 有没有错、漏、歧义 | DOORS 讨论 |
| 5 | 需求基线 | 什么时候冻结，冻结哪一版 | DOORS 基线 |
| 6 | 架构设计 | 系统由哪些部分组成 | EA / Rhapsody |
| 7 | 详细设计 | 模块内部怎么实现 | EA / OpenAPI |
| 8 | 需求分配 | 每条需求由谁实现 | DOORS 链接 |
| 9 | 编码实现 | 把需求写成代码 | Git / GitLab |
| 10 | 单元测试 | 函数和类是否正确 | JUnit / pytest |
| 11 | 集成测试 | 模块之间能不能通 | Postman / JMeter |
| 12 | 系统测试 | 端到端是否符合系统需求 | TestRail / Xray |
| 13 | 验收测试 | 业务是否接受 | TestRail / 客户环境 |
| 14 | 发布上线 | 何时、发多少、怎么回滚 | Jenkins + Argo CD |
| 15 | 变更控制 | 改不改、影响谁、谁批 | DOORS 变更单 |
| 16 | 追溯与度量 | 每条需求能否追到底、过程可不可度量 | DOORS + Power BI |

闭环：**定义（1-5）→ 设计（6-8）→ 实现（9）→ 验证（10-13）→ 交付（14）→ 治理（15-16）**。
每个阶段都是一个“责任落点”，工具只是在这个落点上干活。

## 阶段 1：需求获取

> 核心问题：**谁、在什么场景、想要什么**

### 1.1 在干什么

需求获取拿到的其实是素材，还不是规格。业务方说“要一个刷脸闸机”，你真正要问清的是三件事：谁在用（员工、访客、保洁、安保）、在什么场景用（早高峰排队、访客临时通行、黑名单拦截）、什么条件下会失效（断网、遮挡、临时授权）。这一步的分量在于：后面所有阶段的返工量，大多由这里决定——很多“需求变更”，本质是当初没问清。

### 1.2 用什么工具

| 工具 | 用途 | 主流程度 |
|---|---|---|
| Jira | 需求池、Epic/Story | 互联网标配 |
| Confluence | 访谈记录、方案文档 | 与 Jira 配套 |
| Excel | 小团队需求清单 | 意外地常用 |
| 禅道 / PingCode | 国内一体化研发管理 | 中小团队常见 |

### 1.3 工具边界

这类工具的本质是“记录与流转”，不是“思考”。它们能保证每条想法不丢、有人认领、有状态可查，但判断不了两条需求是否冲突，也排不出优先级。边界就在这：**工具负责不丢，人负责想清**。所以别指望配好工具就等于有了需求管理——工具只在你已经想清楚之后才有价值。

| 能做 | 不能做 |
|---|---|
| 记录与流转需求 | 不解决需求冲突 |
| 按项目/版本归类 | 不判断可行性 |
| 多人协作评论 | 不保证需求质量 |
| 附件与文档关联 | 不会替你思考 |

### 1.4 PM 职责边界

| 档位 | 事项 | 归属说明 |
|---|---|---|
| ✅ PM 主责 | 访谈与场景梳理 | PM 核心产出 |
| ✅ PM 主责 | 干系人清单与需求池质量 | PM 对完整性负责 |
| ⚠️ PM 参与 | 业务目标对齐 | 目标由业务方定，PM 负责翻译 |
| ⚠️ PM 参与 | 竞品分析 | 可委托调研，PM 定方向 |
| ❌ 非 PM 范围 | 需求池工具配置、字段与工作流 | **属于研发/工具链范围** |
| ❌ 非 PM 范围 | 访谈录音转写与归档 | 可由助理或 AI 完成 |
| ❌ 非 PM 范围 | 法务与合规判断 | **属于法务/合规范围** |

### 1.5 优缺点

| 工具 | 优点 | 缺点 |
|---|---|---|
| Jira | 与任务/迭代天然打通，需求池灵活 | 结构化弱，需求追溯靠插件 |
| Confluence | 文档协作强，版本历史清晰 | 不是需求库，无法建立追溯 |
| Excel / 禅道 | 零成本、人人会用 / 中文友好 | 无权限、无追溯 / 复杂追溯弱于专业工具 |

> **结论**：小团队用 Jira + Confluence 足够；一旦出现“同一需求被三个人理解成三样”，就该上结构化需求库了。

### 1.6 常见坑

最常见的坑是**把方案当需求**：业务说“要人脸识别闸机”，你就记成“人脸识别闸机”，而不是“授权人员在 1 秒内完成无感通行”。第二个坑是**只记 happy path**——忘带卡、断网、黑名单、访客临时授权全没写，到测试阶段才炸。第三个坑是**没有验收标准**：写完不知道怎样算做完，最后只能靠“感觉差不多了”上线。

> **交接**：原始需求清单 → 需求分析（分类、优先级、冲突裁决）

## 阶段 2：需求分析

> 核心问题：**哪些做、先做哪个、冲突怎么解**

### 2.1 在干什么

需求分析的核心动作是**做减法**：把 200 条想法收敛成 80 条要做的，并且能说清为什么砍掉那 120 条。同时要把“功能”之外的维度补齐——性能、安全、兼容、可运维，这些指标上线后才暴露，代价最高。

### 2.2 用什么工具

| 工具 | 用途 | 主流程度 |
|---|---|---|
| Jira | 优先级字段、看板 | 主流 |
| Excel | 价值-成本矩阵 | 通用 |
| Confluence | 分析报告 | 主流 |
| 思维导图工具 | 场景与依赖梳理 | 辅助 |

### 2.3 工具边界

分析工具能帮你把分类和优先级**记下来**，但替代不了判断。优先级本质是资源分配，取决于预算、时间窗和组织博弈，工具里那个下拉框只是结果，不是决策过程。边界是：**工具承载结论，不产生结论**。

| 能做 | 不能做 |
|---|---|
| 承载分类与优先级 | 不判断技术可行性 |
| 可视化范围与依赖 | 不替业务做取舍 |
| 记录决策结论 | 不估算工作量 |

### 2.4 PM 职责边界

| 档位 | 事项 | 归属说明 |
|---|---|---|
| ✅ PM 主责 | 需求分类、优先级、范围裁剪 | PM 的核心判断 |
| ✅ PM 主责 | 冲突识别与裁决提议 | PM 组织，业务拍板 |
| ⚠️ PM 参与 | 技术可行性 | 研发评估，PM 不拍板 |
| ⚠️ PM 参与 | 成本与工期估算 | 研发/PMO 主导 |
| ❌ 非 PM 范围 | 架构方案与技术选型 | **属于架构/研发范围** |
| ❌ 非 PM 范围 | 合规与法务判定 | 属于法务范围 |

### 2.5 优缺点

| 工具 | 优点 | 缺点 |
|---|---|---|
| Jira | 优先级字段与看板直观 | 不擅长价值-成本矩阵分析 |
| Excel | 矩阵与打分模型灵活 | 手工维护，需求一变就过期 |
| Confluence | 决策过程与结论沉淀好 | 结论与需求条目不联动 |

> **结论**：优先级永远是人拍的，但拍完必须落进工具，否则三个月后没人记得为什么这么排。

### 2.6 常见坑

最大的坑是**只做功能不做非功能**：清单里全是“支持 xx 功能”，没有一条写响应时间、并发量、可用性，结果系统一上线就崩。第二个坑是**优先级没有依据**，全靠嗓门大小。第三个坑是**冲突不记录**：两个部门要相反的行为，会上没裁决，实现时各做一半。

> **交接**：需求分析报告（范围、优先级、依赖、风险）→ 需求规格化

## 阶段 3：需求规格化

> 核心问题：**怎么写成可验证、可追溯的需求**

### 3.1 在干什么

规格化是把“想要什么”翻译成“可被验证、可被追溯的句子”。难点不在写，而在克制：一条需求只讲一件事，每个形容词都能被量化，每个编号都能被引用。写完之后要经得起三种人的检查——测试能照着它设计用例，开发能照着它估工时，评审能照着它挑毛病。做不到这三点，说明还停留在需求清单阶段。

### 3.2 用什么工具

| 工具 | 用途 | 主流程度 |
|---|---|---|
| IBM DOORS | 强追溯、强基线 | 航空/军工/汽车 |
| Siemens Polarion | ALM 一体化 | 汽车/医疗 |
| Jama Connect | 现代 SaaS | 医疗/半导体 |
| Word / Excel | 轻量，无追溯 | 小项目 |

### 3.3 工具边界

这类工具（以 DOORS 为代表）强在“关系”和“版本”，弱在“表达”和“计算”。它能把 700 条需求和 600 条链接管得清清楚楚，却画不出一张架构图，也跑不了一个测试。边界就在这：**它是需求的数据库，不是研发流水线**。指望它顺手把设计、代码、测试全管了，是选型时最常见的误解。

| 能做 | 不能做 |
|---|---|
| 需求对象、属性、层级 | 画 UML/SysML 图 |
| 追溯链接（需求↔需求↔工件） | 执行代码、跑测试 |
| 基线、版本对比 | 版本分支与合并 |
| 讨论与评审留痕 | 项目管理与工时 |
| 导出 Word/Excel/PDF/ReqIF | 缺陷生命周期管理 |

### 3.4 PM 职责边界

| 档位 | 事项 | 归属说明 |
|---|---|---|
| ✅ PM 主责 | 需求分层与措辞、验收标准 | PM 核心产出 |
| ✅ PM 主责 | 需求编号规则制定 | 规则由 PM 定 |
| ⚠️ PM 参与 | 需求评审会 | PM 组织，结论由评审委员会定 |
| ⚠️ PM 参与 | 属性字段设计 | PM 提业务诉求，字段落地由工具链做 |
| ❌ 非 PM 范围 | DOORS 模块/属性搭建 | **属于研发范围**，PM 只提需求 |
| ❌ 非 PM 范围 | DXL 脚本、批量导入 | **属于研发范围**，PM 可写验证脚本但不进生产 |
| ❌ 非 PM 范围 | 合规工作产品清单 | 属于质量/过程范围 |

### 3.5 优缺点

| 工具 | 优点 | 缺点 |
|---|---|---|
| IBM DOORS | 追溯与基线最强，行业与甲方认可 | 界面老旧、部署重、许可贵 |
| Siemens Polarion | Web 端一体化，需求+测试+缺陷 | 定制成本高，大规模性能一般 |
| Jama Connect | 易用、协作好、SaaS 部署快 | 复杂基线场景弱于 DOORS |
| Word / Excel | 零学习成本，交付直观 | 无追溯、无权限、无法审计 |

> **结论**：强审计、长周期、多方交付选 DOORS；快速迭代、团队小，用 Jira 加结构化模板也够。

### 3.6 常见坑

最常见的坑是**把句子写成愿望**——“系统应快速响应并且界面友好”，一句话里两个指标都不可测，测试没法设计用例，验收只能靠感觉。第二个坑是**层级上瘾**：为了“结构化”拆到六七层，改一条需求要动五个地方，最后没人愿意维护。第三个坑是**只写正文不写属性**：需求看着完整，却没法按优先级排序、按状态统计。

> **交接**：需求规格书（模块 + 对象 + 属性）→ 需求评审

## 阶段 4：需求评审

> 核心问题：**有没有错、漏、歧义**

### 4.1 在干什么

评审的价值不在“开会”，而在**把分歧提前暴露**。同一句话，业务理解成 A，开发理解成 B，测试理解成 C——评审就是让这三种理解撞一次，撞出来的差异就是隐患。所以评审要盯的不是“写得漂不漂亮”，而是“读起来是不是只有一种意思”。

### 4.2 用什么工具

| 工具 | 用途 | 主流程度 |
|---|---|---|
| DOORS 讨论 | 条目级评审留痕 | 与需求直接关联 |
| Confluence | 评审记录 | 通用 |
| Jira | 评审缺陷跟踪 | 互联网 |
| 会议 + 检查单 | 正式评审 | 里程碑 |

### 4.3 工具边界

讨论与评审工具能留存意见、绑定条目、跟踪状态，但它们不判断对错。工具不会告诉你这条需求有歧义，只会如实记录“张三说有问题”。边界是：**工具负责留痕，判断靠人**。

| 能做 | 不能做 |
|---|---|
| 记录意见与结论 | 不判断需求是否正确 |
| 按条关联到需求 | 不会自动发现歧义 |
| 跟踪整改状态 | 不做合规签认 |

### 4.4 PM 职责边界

| 档位 | 事项 | 归属说明 |
|---|---|---|
| ✅ PM 主责 | 组织评审、准备材料、跟踪闭环 | PM 是组织者 |
| ✅ PM 主责 | 决议草稿与整改任务分派 | PM 推动落地 |
| ⚠️ PM 参与 | 评审结论签认 | 由评审委员会/质量签认 |
| ⚠️ PM 参与 | 评审流程与检查单模板 | 质量提供模板 |
| ❌ 非 PM 范围 | 评审流程定义与合规判定 | **属于质量/过程范围** |
| ❌ 非 PM 范围 | 工具配置与模板开发 | 属于研发/工具链范围 |

### 4.5 优缺点

| 工具 | 优点 | 缺点 |
|---|---|---|
| DOORS 讨论 | 意见直接挂在需求条目上 | 讨论功能弱，无流程与结论签认 |
| Confluence | 评论、版本历史与并发编辑好 | 与需求库脱节，改没改要人工核对 |
| Jira | 评审问题可直接转任务跟踪 | 评审结论不落在需求上 |
| 会议 + 检查单 | 灵活，适合里程碑评审 | 记录易丢，问题难统计 |

> **结论**：评审必须有检查单，否则每次评审的深度取决于当天谁在场。

### 4.6 常见坑

第一个坑是**会而不议**：开成汇报会，念一遍需求就散会。第二个坑是**意见不闭环**：会上提了 20 条，改没改没人跟。第三个坑是**评审记录丢失**：半年后追责，找不到当时谁同意了什么。

> **交接**：评审记录与决议 → 需求基线（冻结通过的那一版）

## 阶段 5：需求基线

> 核心问题：**什么时候冻结，冻结哪一版**

### 5.1 在干什么

基线是“从此以后改动要走流程”的那条线。它的价值不在冻结本身，而在**冻结之后能对比**：三个月后有人问“这个功能什么时候加进来的”，你能拿出两版基线 diff 给他看。没有基线，一切变更都只是口头的。

### 5.2 用什么工具

| 工具 | 用途 | 主流程度 |
|---|---|---|
| DOORS 基线 | 需求基线 | 行业标准 |
| Git tag | 代码基线 | 研发侧 |
| 发布管理系统 | 版本归档 | 大型组织 |

### 5.3 工具边界

基线工具能做只读快照和版本对比，但做不了分支和合并。这跟 Git 是两种东西：Git 允许两条线并行开发再合并，需求基线只允许一条主线往前推。边界是：**需求基线是“冻结”，不是“分支”**。

| 能做 | 不能做 |
|---|---|
| 冻结只读快照 | 不做分支与合并 |
| 两版对比、看差异 | 不做审批流 |
| 作为变更起点 | 不自动同步到代码 |

### 5.4 PM 职责边界

| 档位 | 事项 | 归属说明 |
|---|---|---|
| ✅ PM 主责 | 决定基线时机与范围 | PM 判断业务是否稳定 |
| ✅ PM 主责 | 基线说明与对外发布口径 | PM 对内容负责 |
| ⚠️ PM 参与 | 基线策略与版本号规则 | 由 CM 维护 |
| ⚠️ PM 参与 | 基线评审 | 质量/CM 参与 |
| ❌ 非 PM 范围 | 基线创建与比对操作 | **属于 CM/工具链范围** |
| ❌ 非 PM 范围 | 配置管理流程定义 | 属于质量/过程范围 |

### 5.5 优缺点

| 工具 | 优点 | 缺点 |
|---|---|---|
| DOORS 基线 | 只读快照、可对比，审计友好 | 无分支合并，操作偏重 |
| Git tag | 轻量，与代码同源 | 只管代码，管不了需求 |
| 发布管理系统 | 流程规范、可审批 | 与需求库集成成本高 |

> **结论**：基线宁少勿多——一个里程碑一条，别每周都冻。

### 5.6 常见坑

第一个坑是**冻得太早**：需求还没稳定就冻结，后面全是变更，基线失去权威。第二个坑是**冻完直接改**：绕过流程，基线变成摆设。第三个坑是**基线没有说明**：半年后没人知道这版为什么存在。

> **交接**：基线版本（只读快照 + 清单）→ 架构设计

---

## 阶段 6：架构设计

> 核心问题：**系统由哪些部分组成**

### 6.1 在干什么

架构设计回答的是“系统由哪几块组成、边界在哪、谁调用谁”。对 PM 来说，这一步的意义是**把需求翻译成可分工的单元**：哪条需求归哪个子系统，哪个团队负责哪块。架构不合理，后面所有排期都会拧巴。

### 6.2 用什么工具

| 工具 | 用途 | 主流程度 |
|---|---|---|
| Sparx Enterprise Architect | UML/SysML，性价比高 | 国内中型项目 |
| IBM Rhapsody | 与 DOORS 同厂、可仿真 | 汽车/航空 |
| Cameo Systems Modeler | MBSE 标准工具 | 复杂系统/军工 |
| Visio / PlantUML | 轻量画图 | 小项目 |

### 6.3 工具边界

建模工具能画出漂亮的结构，也能做需求到组件的分配，但它们不管需求变更——需求改了，模型不会自动更新。边界是：**模型是快照，不是活文档**；它能表达结构，不能保证同步。

| 能做 | 不能做 |
|---|---|
| 图形化表达结构 | 不管需求变更 |
| 需求分配到组件 | 不校验需求覆盖完整性 |
| 生成代码骨架、可仿真 | 不管理系统测试 |

### 6.4 PM 职责边界

| 档位 | 事项 | 归属说明 |
|---|---|---|
| ✅ PM 主责 | 提供需求输入与业务约束 | PM 是需求方代表 |
| ✅ PM 主责 | 评审架构对需求的覆盖 | 确认每条需求有归属 |
| ⚠️ PM 参与 | 架构方案评审 | 架构师主导，PM 提业务意见 |
| ⚠️ PM 参与 | 接口的业务语义 | 技术契约由研发定 |
| ❌ 非 PM 范围 | UML/SysML 建模 | **属于架构师范围** |
| ❌ 非 PM 范围 | 技术选型、性能与容量设计 | **属于架构/研发范围** |

### 6.5 优缺点

| 工具 | 优点 | 缺点 |
|---|---|---|
| Sparx EA | 性价比高，UML/SysML 覆盖全 | 界面复杂，团队上手慢 |
| IBM Rhapsody | 与 DOORS 同厂，可仿真验证 | 许可贵，偏汽车/航空场景 |
| Cameo | MBSE 能力强，适合复杂系统 | 学习曲线陡，价格高 |
| Visio / PlantUML | 轻量、出图快 | 无模型语义，做不了需求分配 |

> **结论**：架构评审时 PM 只需盯一件事：每条系统需求是否都能在架构里找到归属。

### 6.6 常见坑

第一个坑是**架构脱离需求**：为了技术先进性做了一堆需求用不上的设计。第二个坑是**过度建模**：几百张图，没人看。第三个坑是**架构改了不同步需求**，追溯从此断裂。

> **交接**：架构图与组件划分 → 详细设计

---

## 阶段 7：详细设计

> 核心问题：**模块内部怎么实现**

### 7.1 在干什么

详细设计是“模块内部怎么实现”：类怎么分、接口什么形状、异常怎么处理。对 PM 而言不需要看懂每个类，但需要确认两件事——**业务规则有没有落进去**、**异常路径有没有处理**。这两点漏了，测试阶段一定爆。

### 7.2 用什么工具

| 工具 | 用途 | 主流程度 |
|---|---|---|
| Enterprise Architect | 类图/时序图 | 主流 |
| PlantUML | 文本化建模 | 研发常用 |
| Swagger / OpenAPI | 接口契约 | 接口项目标配 |
| Confluence | 设计文档 | 通用 |

### 7.3 工具边界

设计工具能表达结构和契约，但不会校验“是否覆盖了所有需求”，也不会提醒你“这条需求的异常分支没设计”。边界是：**设计文档保真于设计，不保真于需求**，覆盖度只能靠人对照检查。

| 能做 | 不能做 |
|---|---|
| 表达内部结构与交互 | 不校验是否覆盖全部需求 |
| 定义接口契约 | 不同步需求变更 |
| 生成接口文档与桩代码 | 不保证实现与设计一致 |

### 7.4 PM 职责边界

| 档位 | 事项 | 归属说明 |
|---|---|---|
| ✅ PM 主责 | 校验设计覆盖需求与业务规则 | PM 关注“有没有漏” |
| ✅ PM 主责 | 确认业务异常与边界处理 | 业务规则由 PM 定义 |
| ⚠️ PM 参与 | 接口契约评审 | 研发主导 |
| ⚠️ PM 参与 | 设计评审 | 架构师/研发主导 |
| ❌ 非 PM 范围 | 详细设计本身 | **属于研发范围** |
| ❌ 非 PM 范围 | 代码规范与实现细节 | 属于研发范围 |

### 7.5 优缺点

| 工具 | 优点 | 缺点 |
|---|---|---|
| Enterprise Architect | 类图/时序图完整，可生成文档 | 导出与维护繁琐 |
| PlantUML | 文本化建模，可进 Git 评审 | 图形能力有限 |
| Swagger / OpenAPI | 契约即文档，可生成桩代码 | 只覆盖接口，不覆盖内部设计 |
| Confluence | 易写易读，团队都会用 | 容易过期，无强制约束 |

> **结论**：接口契约（OpenAPI）比设计文档更值得 PM 花时间看，因为它是系统对外的承诺。

### 7.6 常见坑

第一个坑是**设计与需求脱节**，实现出来对不上验收标准。第二个坑是**接口没有契约**，联调全靠猜。第三个坑是**设计文档写完就没人维护**，三个月后与代码完全不符。

> **交接**：详细设计与接口契约 → 需求分配

---

## 阶段 8：需求分配

> 核心问题：**每条需求由谁实现**

### 8.1 在干什么

分配是把“需求”和“实现它的地方”连起来，形成一张矩阵。它的作用有两个：确认没有**无主需求**（谁都不认领），也确认没有**重复承接**（两个团队都做）。这张矩阵还是后面影响分析的基础——改一条需求，顺着矩阵就能找到谁受影响。

### 8.2 用什么工具

| 工具 | 用途 | 主流程度 |
|---|---|---|
| DOORS 链接 | 需求→组件的链接 | 与需求同库 |
| EA 分配矩阵 | 模型内分配 | 架构侧 |
| Excel 矩阵 | 轻量 | 小项目 |

### 8.3 工具边界

分配关系本质是链接：工具能存、能查、能出矩阵，但不会主动告诉你“这条需求没人管”。遗漏只能靠查询或脚本发现。边界是：**工具存关系，完整性靠人核**。

| 能做 | 不能做 |
|---|---|
| 记录需求与组件的对应 | 不自动发现遗漏（需查询/脚本） |
| 生成分配矩阵 | 不判断分配是否合理 |
| 支持按组件反查需求 | 不同步组织调整 |

### 8.4 PM 职责边界

| 档位 | 事项 | 归属说明 |
|---|---|---|
| ✅ PM 主责 | 分配原则与业务边界 | PM 定“谁负责什么业务” |
| ✅ PM 主责 | 确认每条需求有归属 | PM 对完整性负责 |
| ⚠️ PM 参与 | 组件划分 | 架构师主导 |
| ⚠️ PM 参与 | 跨团队需求协调 | PM 推动，组织决策 |
| ❌ 非 PM 范围 | 分配矩阵在模型/需求库中的维护 | **属于研发/工具链范围** |
| ❌ 非 PM 范围 | 组件技术边界定义 | 属于架构师范围 |

### 8.5 优缺点

| 工具 | 优点 | 缺点 |
|---|---|---|
| DOORS 链接 | 分配关系与需求同库，可反查 | 全手工维护，容易漏 |
| EA 分配矩阵 | 图形化直观，架构视角清晰 | 与需求库不同步 |
| Excel 矩阵 | 灵活，适合一次性梳理 | 无追溯，改完就散 |

> **结论**：分配矩阵要在基线前过一遍，比上线后追责便宜得多。

### 8.6 常见坑

第一个坑是**需求没有归属**，上线了不知道是谁做的。第二个坑是**一条需求被多个组件重复承接**，职责冲突。第三个坑是**分配后不更新**，矩阵与实现早已脱节。

> **交接**：需求分配矩阵 → 编码实现（各团队按分配领活）

---

## 阶段 9：编码实现

> 核心问题：**把需求写成代码**

### 9.1 在干什么

编码是把需求变成可执行的东西。对 PM 来说，这一步真正要盯的不是代码质量，而是**需求是否还追得回去**：提交信息里有没有需求编号、分支名有没有、代码注释里有没有。没有这些锚点，半年后没人能解释“这段代码为什么存在”。

### 9.2 用什么工具

| 工具 | 用途 | 主流程度 |
|---|---|---|
| Git | 分布式版本控制 | 事实标准 |
| GitHub / GitLab | 托管、评审、CI | 主流 |
| SVN | 集中式版本控制 | 老项目 |
| IDE（IDEA/VS Code） | 编码 | 通用 |

### 9.3 工具边界

版本控制工具管的是“文本变化”，不是“需求变化”。它能告诉你哪一行什么时候被谁改了，但不能告诉你这次改动对应哪条需求——除非你在提交信息里写了。边界是：**Git 不懂需求，追溯靠约定**。

| 能做 | 不能做 |
|---|---|
| 版本管理、分支合并 | 不懂需求语义 |
| 代码评审 | 不能自动建立需求追溯 |
| 与 CI/CD 集成 | 不保证实现正确 |

### 9.4 PM 职责边界

| 档位 | 事项 | 归属说明 |
|---|---|---|
| ✅ PM 主责 | 需求澄清与验收 | PM 解释“要什么” |
| ✅ PM 主责 | 实现优先级排序 | 决定先做哪条 |
| ⚠️ PM 参与 | 技术方案评审 | 研发主导 |
| ⚠️ PM 参与 | 代码评审 | 可参加但不做主评 |
| ❌ 非 PM 范围 | 编写生产代码 | **属于研发范围** |
| ❌ 非 PM 范围 | 分支策略、代码规范、合并发布 | **属于研发范围** |
| ❌ 非 PM 范围 | 环境与依赖管理 | 属于研发/运维范围 |

### 9.5 优缺点

| 工具 | 优点 | 缺点 |
|---|---|---|
| Git | 分支灵活、历史完整、可回滚 | 学习曲线陡，冲突处理复杂 |
| GitHub / GitLab | 评审、CI、Issue 一体 | 需求追溯仍靠约定 |
| SVN | 集中式简单，权限清晰 | 分支笨重，生态萎缩 |

> **结论**：团队只要坚持一条规矩——提交信息带需求 ID，追溯成本就降一个数量级。

### 9.6 常见坑

第一个坑是**代码不写需求 ID**，上线后无法回答“为什么有这个功能”。第二个坑是**提交信息随意**（fix bug / update），历史等于没有。第三个坑是**长期分支不合并**，最后合并地狱。

> **交接**：代码与提交记录 → 单元测试

---

## 阶段 10：单元测试

> 核心问题：**函数和类是否正确**

### 10.1 在干什么

单元测试是开发对自己代码的“自检”，跑得快、定位准。对 PM 而言，它的价值不在覆盖率数字，而在**回归保护**：改一处不影响另一处，团队才敢频繁发版。

### 10.2 用什么工具

| 工具 | 用途 | 主流程度 |
|---|---|---|
| JUnit / pytest / Jest | 单元测试框架 | 事实标准 |
| JaCoCo / coverage.py | 覆盖率统计 | 配套 |
| SonarQube | 静态扫描与质量门禁 | 企业常用 |
| Mockito 等 | 打桩 | 配套 |

### 10.3 工具边界

单测框架能验证代码逻辑，但验证不了需求——它不知道“这条需求要求 2 秒内响应”。覆盖率工具也只是统计“代码被执行过”，不代表“逻辑正确”。边界是：**覆盖率是下限，不是质量证明**。

| 能做 | 不能做 |
|---|---|
| 快速验证代码逻辑 | 不证明需求被满足 |
| 统计行/分支覆盖率 | 不覆盖集成与端到端 |
| 接入流水线做门禁 | 覆盖率不等于质量 |

### 10.4 PM 职责边界

| 档位 | 事项 | 归属说明 |
|---|---|---|
| ✅ PM 主责 | 关注关键需求是否被单测覆盖 | PM 关注风险点 |
| ✅ PM 主责 | 确认缺陷修复有回归 | PM 关心闭环 |
| ⚠️ PM 参与 | 覆盖率目标设定 | 研发/测试定标准 |
| ⚠️ PM 参与 | 测试策略 | 测试主导 |
| ❌ 非 PM 范围 | 编写与维护单测 | **属于研发范围** |
| ❌ 非 PM 范围 | 流水线与门禁配置 | 属于研发/测试开发范围 |

### 10.5 优缺点

| 工具 | 优点 | 缺点 |
|---|---|---|
| JUnit / pytest / Jest | 生态成熟，易接入流水线 | 只测代码逻辑，不等于需求被满足 |
| JaCoCo / coverage.py | 覆盖率直观，能做门禁 | 覆盖率可被无意义断言刷高 |
| SonarQube | 静态扫描与质量门禁统一 | 规则维护成本，存在误报 |

> **结论**：别拿覆盖率当 KPI，否则一定收获一堆 assert(true)。

### 10.6 常见坑

第一个坑是**为覆盖率写无意义断言**。第二个坑是**只测正常分支**，异常与边界不测。第三个坑是**单测通过就认为需求实现正确**，跳过了系统级验证。

> **交接**：单元测试与覆盖率 → 集成测试

---

## 阶段 11：集成测试

> 核心问题：**模块之间能不能通**

### 11.1 在干什么

集成测试验证的是“模块拼起来还能不能跑”。多数线上事故不在单个模块内部，而在**接口的假设不一致**：A 以为 B 会返回空数组，B 返回了 null。所以这一步的重点是契约与异常传播，不是功能覆盖。

### 11.2 用什么工具

| 工具 | 用途 | 主流程度 |
|---|---|---|
| Postman / Newman | 接口测试 | 主流 |
| JMeter | 接口与性能 | 通用 |
| Testcontainers | 容器化依赖 | 现代做法 |
| TestRail / Xray | 用例管理 | 配套 |

### 11.3 工具边界

接口测试工具能发请求、断言响应、做自动化，但搭不出真实环境；环境不稳定时，测试结果本身就不可信。边界是：**工具验证契约，环境决定结论可信度**。

| 能做 | 不能做 |
|---|---|
| 验证接口契约 | 不覆盖业务全流程 |
| 模拟依赖环境 | 环境不稳定会误判 |
| 自动化回归 | 不替代系统测试 |

### 11.4 PM 职责边界

| 档位 | 事项 | 归属说明 |
|---|---|---|
| ✅ PM 主责 | 确认接口类需求被覆盖 | PM 关注接口承诺 |
| ✅ PM 主责 | 确认跨系统业务规则 | 业务语义由 PM 定 |
| ⚠️ PM 参与 | 联调计划与时间窗 | 测试/研发主导 |
| ⚠️ PM 参与 | 接口变更通知 | 研发发起，PM 传达到业务 |
| ❌ 非 PM 范围 | 环境搭建与依赖准备 | **属于运维/测试开发范围** |
| ❌ 非 PM 范围 | 自动化脚本编写 | 属于测试开发范围 |

### 11.5 优缺点

| 工具 | 优点 | 缺点 |
|---|---|---|
| Postman / Newman | 接口调试与自动化一体 | 复杂业务编排能力弱 |
| JMeter | 接口与性能兼顾 | 脚本维护成本高 |
| Testcontainers | 依赖真实，环境一致性好 | 启动慢，资源占用高 |
| TestRail / Xray | 用例管理与报告规范 | 与需求集成靠导入，非实时 |

> **结论**：集成环境的稳定性，比用例数量更影响交付节奏。

### 11.6 常见坑

第一个坑是**接口改了不通知**，联调时才发现。第二个坑是**测试环境与生产不一致**，测过也白测。第三个坑是**只测连通性**，不测超时、重试、幂等。

> **交接**：集成测试报告 → 系统测试

---

## 阶段 12：系统测试

> 核心问题：**端到端是否符合系统需求**

### 12.1 在干什么

系统测试在接近真实的环境里跑完整业务流，同时验证性能、安全、兼容性这些“非功能”指标。它是上线前最后一道系统性防线，也是唯一能证明“整条业务链走得通”的环节。

### 12.2 用什么工具

| 工具 | 用途 | 主流程度 |
|---|---|---|
| TestRail / Xray / ETM | 用例与执行管理 | 主流 |
| JMeter / LoadRunner | 性能压测 | 通用 |
| Selenium / Playwright | UI 自动化 | 通用 |
| 安全扫描工具 | 漏洞扫描 | 配套 |

### 12.3 工具边界

测试管理工具能组织用例、记录结果、统计通过率，但它只证明“测过的部分没问题”，不能证明“没测的部分没问题”。边界是：**测试证明存在缺陷，不证明没有缺陷**。

| 能做 | 不能做 |
|---|---|
| 端到端验证业务流 | 只证明测过的部分 |
| 性能与容量评估 | 不能证明未测部分 |
| 缺陷记录与统计 | 不替代验收测试 |

### 12.4 PM 职责边界

| 档位 | 事项 | 归属说明 |
|---|---|---|
| ✅ PM 主责 | 验收标准与通过门槛 | PM 定“怎样算过” |
| ✅ PM 主责 | 业务场景与数据准备 | PM 提供真实场景 |
| ⚠️ PM 参与 | 测试方案评审 | 测试主导 |
| ⚠️ PM 参与 | 缺陷优先级判定 | PM 决定是否阻塞 |
| ❌ 非 PM 范围 | 用例设计与执行 | **属于测试范围** |
| ❌ 非 PM 范围 | 缺陷根因分析 | 属于研发范围 |

### 12.5 优缺点

| 工具 | 优点 | 缺点 |
|---|---|---|
| TestRail | 用例与执行管理清晰 | 需求追溯需插件或导入 |
| Xray（Jira） | 与需求、缺陷同平台 | 大规模下性能一般 |
| JMeter / LoadRunner | 性能压测成熟 | 场景设计与脚本门槛高 |
| Selenium / Playwright | UI 自动化生态好 | 脚本脆弱，维护成本高 |

> **结论**：系统测试的通过标准必须在测试开始前定好，否则永远吵不完。

### 12.6 常见坑

第一个坑是**只测功能不测非功能**，上线后性能崩。第二个坑是**通过率造假**：跳过失败用例，指标好看风险更高。第三个坑是**缺陷不定级**，全都标“紧急”，最后没人当回事。

> **交接**：系统测试报告与缺陷清单 → 验收测试

---

## 阶段 13：验收测试

> 核心问题：**业务是否接受**

### 13.1 在干什么

验收测试是业务方用自己的场景、自己的数据，确认“这东西能不能用”。它跟系统测试的区别不在技术，而在**判定权**：系统测试判定“符不符合规格”，验收测试判定“接不接受”。

### 13.2 用什么工具

| 工具 | 用途 | 主流程度 |
|---|---|---|
| TestRail / Excel | 验收用例与结果 | 轻量通用 |
| 客户环境 | 真实数据验证 | UAT |
| Jira | 遗留问题跟踪 | 配套 |

### 13.3 工具边界

验收工具能记录用例与结果，但代替不了业务判断，也没有工具能替你决定“这个缺陷能不能带着上线”。边界是：**工具留证，人签字**。

| 能做 | 不能做 |
|---|---|
| 记录验收结果 | 不代替业务判断 |
| 跟踪遗留问题 | 不证明系统无缺陷 |
| 形成签字依据 | 不解决组织决策 |

### 13.4 PM 职责边界

| 档位 | 事项 | 归属说明 |
|---|---|---|
| ✅ PM 主责 | 组织 UAT、判定是否通过 | PM 代表业务 |
| ✅ PM 主责 | 验收标准解释与争议裁决 | PM 对口径负责 |
| ⚠️ PM 参与 | 遗留缺陷豁免 | 与业务/质量共同决定 |
| ⚠️ PM 参与 | 上线时间窗 | 与运维/业务协商 |
| ❌ 非 PM 范围 | 验收环境准备 | **属于运维范围** |
| ❌ 非 PM 范围 | 缺陷修复 | 属于研发范围 |

### 13.5 优缺点

| 工具 | 优点 | 缺点 |
|---|---|---|
| TestRail / Excel | 简单直接，业务方也会用 | 无流程，签字靠线下 |
| 客户环境 UAT | 最接近真实使用 | 环境与数据准备成本高 |
| Jira | 遗留问题跟踪方便 | 验收结论不结构化，难归档 |

> **结论**：验收标准要在需求阶段就写进需求，而不是验收当天现编。

### 13.6 常见坑

第一个坑是**验收标准模糊**，最后靠感觉验收。第二个坑是**用户不参与**，上线后才发现不合用。第三个坑是**带缺陷上线没有书面豁免**，出问题无法界定责任。

> **交接**：验收报告与签字 → 发布上线

---

## 阶段 14：发布上线

> 核心问题：**何时、发多少、怎么回滚**

### 14.1 在干什么

发布是把“测试通过的版本”变成“用户能用的版本”，核心诉求是**可重复、可回滚、可观测**。一次发布出问题不可怕，可怕的是回不去、也看不出来。

### 14.2 用什么工具

| 工具 | 用途 | 主流程度 |
|---|---|---|
| Jenkins / GitLab CI | 构建流水线 | 主流 |
| Nexus / Harbor | 制品与镜像仓库 | 主流 |
| Docker / Kubernetes | 容器与编排 | 主流 |
| Argo CD / Helm | GitOps 发布 | 现代做法 |
| Prometheus / Grafana | 监控告警 | 主流 |

### 14.3 工具边界

这条链上的工具（CI、制品库、容器、部署、监控）能力很强，但它们**完全不知道需求的存在**：只管“这个包能不能跑起来”，不管“这个包实现了哪条需求”。边界是：**交付工具链与需求管理天然割裂，只能靠标签与注解关联**。

| 能做 | 不能做 |
|---|---|
| 自动化构建与部署 | 完全不知道需求的存在 |
| 环境一致性 | 不管理需求变更 |
| 版本回滚 | 不做业务验收 |
| 监控与告警 |  |

### 14.4 PM 职责边界

| 档位 | 事项 | 归属说明 |
|---|---|---|
| ✅ PM 主责 | 上线范围、时间窗、灰度比例 | PM 决定“发什么、何时发” |
| ✅ PM 主责 | 发布说明与业务通知 | PM 对外口径 |
| ⚠️ PM 参与 | 发布方案与回滚预案 | SRE/研发主导 |
| ⚠️ PM 参与 | 业务监控指标 | PM 提业务指标 |
| ❌ 非 PM 范围 | 流水线配置、镜像构建 | **属于研发范围** |
| ❌ 非 PM 范围 | K8s 部署、扩缩容 | **属于运维/SRE 范围** |
| ❌ 非 PM 范围 | 告警规则与值班 | 属于 SRE 范围 |

### 14.5 优缺点

| 工具 | 优点 | 缺点 |
|---|---|---|
| Jenkins | 插件生态最全，什么都能接 | 配置复杂，流水线维护成本高 |
| GitLab CI | 与代码同平台，YAML 简洁 | 深度定制不如 Jenkins |
| Nexus / Harbor | 制品与镜像管理成熟 | 与需求完全无关联 |
| Argo CD | GitOps 可审计，回滚快 | 依赖 Git 规范与集群权限 |
| Prometheus / Grafana | 开源、指标能力强 | 告警设计与维护需要经验 |

> **结论**：上线的可控性取决于回滚速度，而不是发布次数。

### 14.6 常见坑

第一个坑是**制品没有版本语义**，不知道这个包对应哪版需求。第二个坑是**部署记录与变更单脱节**，出事查不到根因。第三个坑是**告警不带业务维度**，只知道 CPU 高，不知道哪个功能受影响。

> **交接**：发布记录与监控数据 → 变更控制

---

## 阶段 15：变更控制

> 核心问题：**改不改、影响谁、谁批**

### 15.1 在干什么

变更控制回答四个问题：变了什么、影响谁、谁批准、改完没。它不是为了“卡住变更”，而是让变更**可追溯、可回滚、可解释**——半年后被问“这个功能什么时候改的、谁批的”，你能拿出记录。

### 15.2 用什么工具

| 工具 | 用途 | 主流程度 |
|---|---|---|
| DOORS 变更单 | 登记与关联需求 | 与需求同库 |
| DOORS 可疑链接 | 上游改了自动标记下游 | 追溯强 |
| Jira Workflow | 审批流 | 主流 |
| ServiceNow | 企业级审批 | 大型组织 |

### 15.3 工具边界

需求工具能标记“可疑链接”（上游改了，下游被标黄），但做不了审批流；审批流工具能做流程，却不知道需求之间的依赖。边界是：**能力被切成了两半，靠集成拼起来**。

| 能做 | 不能做 |
|---|---|
| 记录变更与理由 | 不做审批流（需外部系统） |
| 标记可疑链接 | 不自动评估技术影响 |
| 统计变更数量与状态 | 不自动回归测试 |

### 15.4 PM 职责边界

| 档位 | 事项 | 归属说明 |
|---|---|---|
| ✅ PM 主责 | 变更必要性与优先级 | PM 决定改不改 |
| ✅ PM 主责 | 影响范围确认与需求文本更新 | PM 对需求负责 |
| ⚠️ PM 参与 | 变更审批（CCB） | 委员会决策，PM 汇报 |
| ⚠️ PM 参与 | 技术影响评估 | 研发评估，PM 汇总 |
| ❌ 非 PM 范围 | 变更单系统配置与流程 | **属于工具链/质量范围** |
| ❌ 非 PM 范围 | 回归测试执行与代码修改 | **属于测试/研发范围** |

### 15.5 优缺点

| 工具 | 优点 | 缺点 |
|---|---|---|
| DOORS 变更单 | 与需求同库，可疑链接自动标记 | 没有审批流，流程能力弱 |
| Jira Workflow | 审批流灵活，可自定义状态机 | 与需求库状态不同步 |
| ServiceNow | 企业级流程与审计 | 重，实施周期长 |

> **结论**：变更的成本不在改需求本身，而在同步下游——用例、代码、部署，一个都不能漏。

### 15.6 常见坑

第一个坑是**只改需求不改测试**，用例还是老的。第二个坑是**不做影响分析**，改一处崩三处。第三个坑是**变更单不闭环**，状态永远停在“处理中”。

> **交接**：变更记录与影响清单 → 追溯与度量

---

## 阶段 16：追溯与度量

> 核心问题：**每条需求能否追到底、过程可不可度量**

### 16.1 在干什么

追溯是把“需求—设计—代码—用例—发布”串成一张网，度量是把这张网的状态变成数字。二者的关系是：**没有追溯，度量就是假的**——覆盖率、通过率全都建立在链接完整的前提上。

### 16.2 用什么工具

| 工具 | 用途 | 主流程度 |
|---|---|---|
| DOORS 链接与矩阵 | 追溯关系 | 行业标准 |
| Power BI / Tableau | 指标看板 | 主流 |
| Grafana | 实时看板 | 运维侧 |
| Excel / CSV | 一次性分析 | 通用 |

### 16.3 工具边界

追溯工具能存链接、出矩阵，但链接是**人建的**；度量工具能算指标，但数据来自各系统导出。边界是：**工具不生产关系，也不生产数据，只做汇总与呈现**。

| 能做 | 不能做 |
|---|---|
| 存储链接关系 | 不产生原始数据 |
| 生成矩阵与覆盖率 | 不保证链接完整（靠人维护） |
| 导出数据做分析 | 不替代决策 |

### 16.4 PM 职责边界

| 档位 | 事项 | 归属说明 |
|---|---|---|
| ✅ PM 主责 | 指标口径（什么算“覆盖/通过”） | 口径错了指标全废 |
| ✅ PM 主责 | 覆盖率目标与复盘改进 | PM 用数据驱动 |
| ⚠️ PM 参与 | 数据源接入方案 | 研发/BI 主导 |
| ⚠️ PM 参与 | 指标实现与校验 | BI 实现，PM 验收口径 |
| ❌ 非 PM 范围 | 数据管道、埋点开发 | **属于研发范围** |
| ❌ 非 PM 范围 | BI 建模与看板制作 | 属于 BI/数据范围 |

### 16.5 优缺点

| 工具 | 优点 | 缺点 |
|---|---|---|
| DOORS 链接与矩阵 | 追溯的行业标准做法 | 链接靠人维护，容易断 |
| Power BI | 可视化强，易分享 | 依赖数据质量与刷新时效 |
| Tableau | 交互分析能力强 | 许可贵 |
| Grafana | 实时看板好，适合运维指标 | 业务语义弱，不适合需求度量 |

> **结论**：追溯覆盖率是最值得盯的单一指标——它一低，其他指标全部失真。

### 16.6 常见坑

第一个坑是**为指标而指标**，覆盖率刷到 100% 但测的是废话。第二个坑是**各工具口径不一致**，覆盖率与通过率对不上。第三个坑是**只看单点数字不看趋势**，数字好看但风险在积累。

> **交接**：追溯矩阵与指标 → 下一轮需求获取（形成闭环）

- 中小团队：禅道/PingCode 一体化，够用但深度不足。
- 趋势：国产化替代在部分行业推进。
