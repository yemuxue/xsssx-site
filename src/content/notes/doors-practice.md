> 这次落地的对象是一家做门禁与能源管理的团队：需求散在 20 多份 Excel 和 Word 里，评审靠邮件，变更靠"我记得改过"。
> 三个星期后，需求进了 DOORS：11 个模块、995 个对象、725 条需求、662 条追溯链接，导入一次 12 秒，校验 100% 通过。
>
> 这篇复盘讲清四件事：**这套东西是什么、我们怎么落的、能力边界在哪、什么情况下别用**。

## 先说结论

1. **价值不在表单，在对象与链接。** 需求一旦是对象，才能回答"谁引用它、改了影响谁、当时谁同意的"。
2. **瓶颈不在 DOORS，在数据准备。** 我们 80% 的时间花在把 Excel 规范成可导入的结构。
3. **它是需求治理工具，不是研发协作平台。** 协作、迭代、看板这些事，它做不了，也不该指望它做。

## 一、认识这套东西：模型与架构

### 1.1 四层数据模型

| 概念 | 是什么 | 类比 |
|---|---|---|
| Folder | 项目文件夹，按 00–07 分层 | 目录 |
| Module | 一张需求表，每行一个对象 | 工作表 |
| Object | 一条需求，或一个章节标题 | 一行 |
| Link | 对象之间的有向关系，可跨模块 | 超链接 |

关键设计：**链接不写进正文，而是独立对象**。所以它才能跨模块、才能被统计成覆盖率，而不是一句"见 3.2 节"。

### 1.2 架构：两层 C/S + 自研对象库

| 组件 | 说明 |
|---|---|
| `doors.exe` | 64 位 Windows 客户端 |
| `doorsd.exe` | 32 位 Windows 服务 |
| `data/v6data` | 自研对象库，863 个文件 |
| TCP 36677 | 客户端与服务之间的本地连接 |
| DXL / COM | 旁路集成：批处理、自动化 |
| ReqIF / XML | 与外部工具交换数据 |

没有外部关系库，也没有 Web 前端。这决定了后面所有的坑：**所有自动化都必须挂在一个已登录的客户端上**。


### 1.3 三个设计决定带来的后果

| 设计 | 好处 | 代价 |
|---|---|---|
| 链接是独立对象（LinkModule / LinkSet） | 能跨模块、能统计、能导出矩阵 | 链接一多，建链比建对象慢两个数量级 |
| 客户端持有连接（C/S） | 权限与一致性由服务端统一管 | 所有自动化都依赖一个已登录的客户端 |
| 基线是只读快照 | 对比干净、可审计 | 没有分支，不能像 Git 那样并行后合并 |

这三条不是缺陷，是取舍。选它之前，先确认自己能接受这三个代价。

## 二、问题与用户

### 2.1 三个结构性死角

| 死角 | 表现 | 后果 |
|---|---|---|
| 没有身份 | 单元格没有编号，引用靠"第 3 页那个登录需求" | 讨论无法对齐 |
| 没有关系 | 需求、设计、测试之间没有链接 | 覆盖率说不清，变更必然漏测 |
| 没有快照 | 改完就覆盖，历史不可回溯 | 查不到"当时是怎么定的" |

文档工具解决不了这三个问题——Word 再强也没有对象模型，Excel 再灵活也没有链接和基线。

### 2.2 四类人，四种诉求

| 角色 | 关心什么 | 在 DOORS 里做什么 |
|---|---|---|
| 产品 / 需求工程师 | 需求全不全、评审过没过 | 写需求、发起评审、维护变更单 |
| 系统 / 设计工程师 | 需求怎么落到子系统 | 建分解结构、做需求分配 |
| 测试 | 每条需求有没有用例覆盖 | 建用例、挂追溯链接 |
| 评审 / 审计 | 谁在什么时候改了什么 | 看基线、看讨论、导审计件 |

最常见的误区：把 DOORS 当成"需求工程师一个人的工具"。结果需求进来了，设计和测试不进来，链接永远是空的——覆盖率永远算不出来。

## 三、怎么落地：V 模型 + 一条可重跑的流水线

### 3.1 8 层 V 模型

| 层级 | 模块 | 对象数 | 定位 |
|---|---|---:|---|
| L1 用户需求 | `UR_用户需求` | 30 | 业务方视角 |
| L2 系统需求 | `SYS_系统需求规格` | 97 | 系统级能力 |
| L3 子系统需求 | `SEC` / `NRG` / `ACS` | 90 / 88 / 77 | 三大子系统 |
| L4 软件需求 | `SW_平台软件需求` | 90 | 可开发粒度 |
| L5 验证用例 | `TC_测试用例规格` | 93 | 按测试层级分派 |
| L6 代码单元 | `CODE_代码单元` | 90 | 实现物 |

辅助模块：接口需求 70 条、测试执行记录 93 条、变更单 15 条。

**为什么不是 5 层**：5 层缺了"子系统"这一跳。安防、能源、门禁由三支团队负责，没有 L3，需求分配就没有落脚点，测试也不知道该找谁确认。

**层数不是越多越好**：有团队做到 12 层，结果花在"放对位置"上的时间超过写需求本身。上限应该是团队的组织边界。

### 3.2 流水线：从 CSV 到库

业务方只会用 Excel，所以真正要设计的是**从表格到库的通道**。

![F01 需求进库流水线](/docs/doors/figures/F01-需求流水线.png)

*图 F01 · CSV → DXL → DOORS → 自动校验 → 交付。校验不通过不进入交付。*

三个硬约束：

| 约束 | 为什么 |
|---|---|
| 输入只能是 CSV | 不能要求业务方装工具 |
| 中间产物是 DXL | 可读、可 diff、可重放，出错能定位到行 |
| 结束必须自动校验 | "跑完了"不等于"跑对了" |

五步命令与产物：

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\tools\gen-data.ps1     # -> requirements.csv（767 行）
powershell -NoProfile -ExecutionPolicy Bypass -File .\tools\csv2dxl.ps1      # -> import-all.dxl（1691 行）
powershell -NoProfile -ExecutionPolicy Bypass -File ..\doors\doors-run.ps1 `
  -DxlFile .\dxl\import-all.dxl -WaitSeconds 900                              # -> 5 文件夹 + 7 模块 + 767 对象
powershell -NoProfile -ExecutionPolicy Bypass -File .\tools\verify.ps1        # -> 逐模块比对数量
powershell -NoProfile -ExecutionPolicy Bypass -File .\tools\link-report.ps1   # -> 662 条链接与覆盖报告
```

校验日志是整条链路里最值钱的东西，它让"导入成功"变成可验证的事实：

```
import start
folder 01 系统需求: exists
folder 02 子系统需求: created
SYS: created (97 reqs, 24 headings)
SEC: created (90 reqs, 23 headings)
import done
```

### 3.3 CSV 的 14 个字段

| 字段 | 说明 | 示例 |
|---|---|---|
| Module / ModuleName | 模块代号与模块名 | `SEC` / `SEC_安防子系统需求` |
| Folder | 所属项目文件夹 | `02 子系统需求` |
| Kind | 章节 / 小节 / 需求 | `需求` |
| Chapter | 所属章节 | `3.2 远程开门` |
| ReqId | 需求编号（仅需求行） | `SEC-0042` |
| Title / Desc | 标题与正文 | `门禁远程开门…` |
| Type | 功能 / 性能 / 安全 / 接口 / 可靠性 | `功能` |
| Priority | 高 / 中 / 低 | `高` |
| Method | 测试 / 演示 / 分析 / 检查 | `测试` |
| Status | 已评审 / 待评审 / 草稿 | `已评审` |
| Owner / Source | 责任人、来源 | `张伟` / `客户需求` |

**一个必须做的取舍**：DOORS 9.6 用 DXL 动态建属性列很麻烦，我们把元数据内嵌进正文：

```
SEC-0042 门禁远程开门：系统应支持门禁远程开门，权限下发在 10 秒内生效。
【类型:功能｜优先级:高｜验证:测试｜状态:已评审｜责任人:张伟｜来源:客户需求】
```

好处是任何空库都能导；代价是不能按属性筛选。试点阶段"能跑通"比"字段漂亮"更重要。

## 四、五项能力，逐一验证

### 4.1 编写：模块化编辑

以表格形式编写，每行是带属性的对象。左侧大纲把章节和需求同屏，可折叠跳转；`Object Heading` 负责编号 1 → 1.1 → 1.1.1，导出时保留层级。

![模块编辑](/docs/doors/screenshots/module.png)

*模块视图：章节与需求同屏，行尾箭头显示链接方向。*

### 4.2 管理：属性、视图与查找

同一份需求，按角色与阶段呈现不同视图：列可自定义（属性、链接指示符、讨论标记），列 + 排序 + 过滤可另存为视图；查找用 Ctrl+F，定位用 Ctrl+G。

### 4.3 追溯：链接与矩阵

![追溯矩阵](/docs/doors/screenshots/matrix.png)

*矩阵视图：横轴测试用例、纵轴系统需求，空白格就是没覆盖的地方。*

对象级要分清两种链接：**紫色 ▶ 出链、橙色 ◀ 入链**。左键只提示路径，右键才弹出目标列表——这个小设计避免误点，但也劝退了不少新人。

覆盖率的分母最容易出错。有人说"我们 92%"，问三个问题就崩了：

| 口径要素 | 我们的定义 |
|---|---|
| 分母 | 仅 `Object Text` 且状态「已评审」的对象 |
| 分子 | 至少一条 out-link 指向测试用例的需求 |
| 排除 | 章节标题、废弃需求、占位行 |
| 时点 | 基于某次基线快照 |

### 4.4 治理：评审、变更与基线

- **讨论**：右键对象新建讨论，意见挂在对象上，不改进正文
- **变更**：CR 单通过链接关联需求，改前先查影响面，本库共 15 张 CR
- **基线**：启用基线集，可建 1.0 / 1.1 并原生比较
- **历史**：谁在何时改了什么，1 次创建 + 2 次改正文 + 3 次建出链都留痕

### 4.5 交付：导出与集成

| 方式 | 能力 |
|---|---|
| 文件 → 导出 | Excel / RTF / HTML / 纯文本 / FrameMaker，跟随当前视图 |
| 编辑 → DXL | 批量建目录、导入、建链、校验（3459 个函数签名） |
| PDF | 走 Ctrl+P 打印 |
| 交换 | ReqIF / XML，可与外部工具互通 |


### 4.6 五项能力小结

| 能力 | 具体表现 | 我们用它做什么 |
|---|---|---|
| 单一数据源 | 995 个对象、11 个模块集中在一个库 | 替代 20 多份散落的 Excel |
| 属性可扩展 | 类型、优先级、验证、状态、责任人、来源 | 支撑筛选与统计 |
| 全链追溯 | 662 条链接，UR→SYS→SUB→SW→CODE→TC | 覆盖率与影响面 |
| 变更可控 | CR 单 + 基线 + 讨论留痕 | 审计与回滚 |
| 交付可导出 | Excel / RTF / HTML / FrameMaker | 交付件自动生成 |

> 这五项里，前两项 Excel 加把劲也能做到；真正拉开差距的是后三项——追溯、变更、交付，都依赖"对象 + 链接"这个底座。

## 五、基线：红线对比实录

基线不是"备份"，是**给变更一个可比较的参照物**。

![F03 基线与变更影响](/docs/doors/figures/F03-基线与变更.png)

*图 F03 · 改动前后各打一个基线，差异只是起点，影响面要顺着链接找下游。*

原生基线的六个动作：

| 步骤 | 操作 |
|---|---|
| 1 | 建「基线集定义」 |
| 2 | 把模块加入定义 |
| 3 | 建「基线集」（版本） |
| 4 | 给模块打第一个基线 |
| 5 | 改需求，再打第二个基线 |
| 6 | 文件 → 基线 → 比较（红线视图） |

真实对比结果：**4 条需求发生变更**（`SYS-0015 / 0016 / 0018 / 0045`），修改 4、新增 0、删除 0；其中一条把响应时间从 3 秒改成 2 秒，另一条另有新增文本，`Object Text` 变更、其余属性不变。

![基线红线对比](/docs/doors/screenshots/native-baseline-compare.png)

*红线视图：改前/改后逐对象比对，只标文本差异。*

**差异 ≠ 影响面**，这组概念最容易混：

| 概念 | 含义 | 怎么得到 |
|---|---|---|
| 差异 | 哪些对象内容变了 | 比较两个基线 |
| 影响面 | 哪些下游要跟着改 | 差异对象 + 链接可达的下游集合 |

只做差异会漏改测试；做到影响面，才知道要通知谁、重跑哪些用例。

## 六、十个坑与六项限制

| # | 坑 | 现象 | 解法 |
|---|---|---|---|
| 1 | 中文编码三套并存 | 导进去是乱码 | 全链路 UTF-8，DXL 带 BOM |
| 2 | `create()` 是相对路径 | 以为建在根目录 | 先 `cd` 到目标文件夹 |
| 3 | 新对象插到顶部 | 顺序全反 | 倒序插入或导入后重排 |
| 4 | 重复导入报错 | 第二次跑抛异常 | 导入前查重，做成幂等 |
| 5 | DXL 语法怪癖 | 转义与括号规则不同 | 小批量试跑看行号 |
| 6 | 报错弹模态框 | 无人值守时挂死 | 执行器轮询自动点掉 |
| 7 | 路径要用正斜杠 | 反斜杠被吃掉 | 统一 `/` |
| 8 | 模块不能建在根目录 | 报路径错 | 先建项目文件夹 |
| 9 | 校验只看总数 | 总数对但模块错位 | 逐模块比对 |
| 10 | 没写回滚 | 导错只能手工删 | 每步留快照 |

六项限制（也是选型时要认的账）：

| 限制 | 影响 |
|---|---|
| DXL 报错即弹窗 | 阻塞 COM 调用，无人值守不可靠 |
| 中文脚本要转 GBK | 编码处理复杂度上一个台阶 |
| 基线 DXL 接口返回 false | 自动化打基线得绕路 |
| 无 Web 前端 | 远程/移动协作基本没有 |
| 无分支合并 | 只有一条主线，不能像 Git 并行 |
| 与研发工具链割裂 | 代码、流水线、看板都要另外接 |

一句话：**优势在需求治理，短板在协作与研发一体化。**


### 6.3 五个高频问题

| 问题 | 现象 | 处理 |
|---|---|---|
| 导入后中文乱码 | 显示 `??` 或方块 | 检查 CSV 与 DXL 是否都带 BOM、客户端语言包是否装 |
| 第二次导入失败 | 模块已存在，`create()` 报错 | 加存在性判断，或换库重跑 |
| 链接建不上 | 提示目标对象不存在 | 确认 ReqId 在目标模块内唯一 |
| 校验数量对不上 | 差几个对象 | 多为章节行被当成需求行，检查 `Kind` 列 |
| 基线比较看不到差异 | 比的是同一版本 | 确认选的是两个不同基线集 |


## 七、边界与选型

### 7.1 16 个阶段里，它管到哪

| # | 阶段 | 在干什么 | 工具边界 |
|---|---|---|---|
| 1 | 需求获取 | 问清谁在用、什么场景 | 只记录想法，不判断冲突 |
| 2 | 需求分析 | 200 条收敛到 80 条 | 优先级是资源分配，工具只存结果 |
| 3 | **需求规格化** | 翻译成可验证、可追溯的句子 | 强在关系与版本，弱在表达 |
| 4 | **需求评审** | 让三种理解撞一次 | 留意见，不判对错 |
| 5 | **需求基线** | 冻结之后能对比 | 做不了分支合并 |
| 6 | 架构设计 | 翻译成可分工的单元 | 模型是快照，不随需求更新 |
| 7 | 详细设计 | 模块内部怎么实现 | 不校验是否覆盖全部需求 |
| 8 | **需求分配** | 需求与人/组件的矩阵 | 存关系，完整性靠查询 |
| 9 | 编码实现 | 需求要能追回代码 | 不懂需求，除非提交写编号 |
| 10–13 | 测试 | 单测 → 集成 → 系统 → 验收 | 证明测过的没问题，不证明没测的 |
| 14 | 发布上线 | 可重复、可回滚、可观测 | 发布链不知道需求存在 |
| 15 | **变更控制** | 变了什么、影响谁、谁批 | 做不了审批流 |
| 16 | **追溯与度量** | 把网串起来 | 链接是人建的，指标靠导出 |

真正只有它能做的只有三个：**规格化、基线、追溯**。

### 7.2 一条需求的完整旅程

**第 1 天 · 获取。** 业务方说"访客要能刷脸进园区"。这是素材，不是需求：谁审批、几点有效、失败怎么办，都没说。

**第 3 天 · 规格化。** 落成 `UR-0007 访客刷脸入园：访客经被访人确认后，可在预约时段内刷脸入园，失败时前台可人工放行。`

**第 5 天 · 评审。** 安保提出"夜间不允许访客入园"，拆成独立的 `SYS-0031`，而不是塞进原句。评审的价值就是把隐含假设逼出来。

**第 2 周 · 分配。** `SYS-0031` 分解到 `SEC` 下三条软件需求，分别对应门禁控制器、人脸服务、消息推送。

**第 3 周 · 测试。** 三条软件需求各挂 1–2 个用例，矩阵上 `UR-0007` 这一行终于有了实心点。

**第 6 周 · 基线。** 打基线 v1，完整链路：1 条用户需求 → 1 条系统需求 → 3 条软件需求 → 4 个用例。

**第 3 个月 · 变更。** "访客可以带同行人"：影响面是 1 条系统需求、2 条软件需求、3 个用例要重跑。

没有链接，就只能靠人回忆还影响哪儿——漏掉的用例会在上线后变成线上问题。

### 7.3 什么时候别用

| 信号 | 建议 |
|---|---|
| 需求 < 100 条，团队 < 5 人 | Markdown + Git，更轻也够用 |
| 没有合规/审计要求 | 先把流程跑顺，不必上重工具 |
| 设计和测试不参与 | 别上——链接建不起来，覆盖率是假的 |
| 没人愿意当需求库管理员 | 别上——结构和口径需要人维护 |
| 只想"把文档存起来" | 网盘或 Wiki 更合适 |

### 7.4 竞品定位

| 场景 | 选择 |
|---|---|
| 强监管 + 追溯硬指标，能接受 C/S | 继续用 DOORS 9.x，补协作短板 |
| 要 Web 协作、跨工具链 | DOORS Next / Polarion / Jama |
| 轻量研发管理、小团队 | 禅道这类 |
| 只写文档、不需要追溯 | Excel / Word |


### 7.5 换成真实业务数据

| 步骤 | 做什么 | 注意 |
|---|---|---|
| 1 | 只换数据 | 按 14 个字段填表，先跑 1 个模块验证 |
| 2 | 加字段 | CSV 加列，同步改 `csv2dxl.ps1` 的映射 |
| 3 | 要属性列 | 先在 GUI 给模板模块定义属性，再改 DXL 按属性名赋值 |

顺序不能反：先全量后属性，一旦属性定义出错，全部数据都要重导。


## 八、如果重来一次

| 教训 | 下次怎么做 |
|---|---|
| 先定口径，再跑数据 | 覆盖率、状态、层级先写成一页纸，全员确认 |
| 先做小批量闭环 | 先导 1 个模块跑通导入 → 校验 → 报告，再放全量 |
| 链接和需求同时进 | 导完立刻建链，别等"以后补" |
| 把校验做成门禁 | 数量不符直接 fail，不给"先跑通再修"的侥幸 |
| 培训四类人 | 设计不建链、测试不挂用例，这套东西就是个文档库 |
