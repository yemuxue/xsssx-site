> 这次落地的对象是一家做门禁与能源管理的团队：需求散在 20 多份 Excel 和 Word 里，评审靠邮件，变更靠"我记得改过"。
> 三个星期后，需求进了 DOORS：11 个模块、995 个对象、725 条需求、662 条追溯链接，导入一次 12 秒，校验 100% 通过。
>
> 这篇复盘不讲软件说明书，讲**产品上做对了什么、做错了什么、下次怎么改**。

## 先说结论

三条判断，后面每一节都在为它们提供证据。

1. **工具的价值不在表单，在对象与链接。** 需求一旦是对象，才能回答"谁引用它、改了影响谁、当时谁同意的"。
2. **落地的瓶颈不在 DOORS，在数据准备。** 我们 80% 的时间花在把 Excel 规范成可导入的结构，而不是点界面。
3. **自动化必须可校验、可重跑。** 导入脚本真正值钱的部分不是"DXL 写得多漂亮"，而是"跑完能自己证明数量对得上"。

## 一、问题：需求在 Excel 里的三个死角

接手时的状态很典型：需求散在 20 多份文件里，同一件事有三个版本；评审在邮件里进行，结论靠翻聊天记录；有人问"这条需求测了没有"，只能靠人肉回忆。

这不是"文件格式不好看"，是三个结构性死角：

| 死角 | 表现 | 后果 |
|---|---|---|
| 没有身份 | 单元格没有编号，引用只能靠"第 3 页那个登录需求" | 讨论无法对齐，评审各说各的 |
| 没有关系 | 需求、设计、测试之间没有任何链接 | 覆盖率说不清，变更必然漏测 |
| 没有快照 | 改完就覆盖，历史不可回溯 | 出问题查不到"当时是怎么定的" |

**产品判断**：这三个死角不是文档工具能解决的。Word 再强也没有对象模型，Excel 再灵活也没有链接和基线。要解决，必须换成有"对象 + 链接 + 基线"三件套的工具——这就是 DOORS 的位置。

## 二、用户是谁：四类人，四种诉求

工具落地的成败，往往取决于有没有服务好这四类人中的每一类。

| 角色 | 关心什么 | 在 DOORS 里做什么 |
|---|---|---|
| 产品 / 需求工程师 | 需求全不全、评审过没过 | 写需求、发起评审、维护变更单 |
| 系统 / 设计工程师 | 需求怎么落到子系统 | 建分解结构、做需求分配 |
| 测试 | 每条需求有没有用例覆盖 | 建测试用例、挂追溯链接 |
| 评审 / 审计 | 谁在什么时候改了什么 | 看基线、看讨论记录、导审计件 |

一个常见误区：把 DOORS 当成"需求工程师一个人的工具"。结果就是需求进来了，设计和测试不进来，链接永远是空的——覆盖率永远算不出来，变更影响永远分析不了。

**所以要落地的不是软件，是"四类人共同维护一份数据"的协作约定。** 这句话听起来虚，但它是这个项目里最真实的教训：工具上线第一周，只有一个人在填数据，第二周就停了。

## 三、产品判断：8 层 V 模型

结构化不是把需求分个类，而是定义清楚"从上到下怎么分解、从下到上怎么验证"。

### 3.1 最终落成的结构

我们把需求分成 8 层，形状是一个 V：左边一路分解下去，右边一路验证上来。

| 层级 | 模块 | 对象数 | 定位 |
|---|---|---:|---|
| L1 用户需求 | `UR_用户需求` | 30 | 业务方视角，最上游 |
| L2 系统需求 | `SYS_系统需求规格` | 97 | 系统级能力 |
| L3 子系统需求 | `SEC` / `NRG` / `ACS` | 90 / 88 / 77 | 三大子系统 |
| L4 软件需求 | `SW_平台软件需求` | 90 | 可开发粒度 |
| L5 验证用例 | `TC_测试用例规格` | 93 | 按测试层级分派 |
| L6 代码单元 | `CODE_代码单元` | 90 | 实现物 |

辅助模块：接口需求 70 条、测试执行记录 93 条、变更单 15 条。

### 3.2 为什么不是 5 层

5 层的经典结构是"用户需求 → 系统需求 → 软件需求 → 测试 → 代码"，看起来够用。但实际项目里，安防、能源、门禁三个子系统由不同团队负责：

- 没有 L3，需求分配到不了具体团队，只能停在"系统需求"这一层
- 测试不知道该找谁确认，链接只能挂到系统需求上
- 变更影响分析到 L2 就断了，无法判断"这条改动影响哪个子系统"

多一层，维护成本高一点；换来的是"每条需求都知道自己属于哪个子系统"。这个交换在这个项目里是划算的。

### 3.3 层数不是越多越好

一个反例：有团队把层级做到 12 层，结果需求工程师花在"放对位置"上的时间超过了写需求本身。层数的上限应该是**团队的组织边界**——有几支团队负责，就分几层，再多就是自嗨。

## 四、方案：一条可重跑的流水线

需求不可能直接在 DOORS 里敲——业务方给的是 Excel。所以真正要设计的是**从表格到库的通道**。

![F01 需求进库流水线](/docs/doors/figures/F01-需求流水线.png)

*图 F01 · 流水线：CSV → DXL → DOORS → 自动校验 → 交付。校验不通过不进入交付。*

### 4.1 三个硬约束

| 约束 | 为什么 |
|---|---|
| 输入只能是 CSV | 业务方只会用 Excel，不能要求他们装工具 |
| 中间产物是 DXL | 可读、可 diff、可重放，出问题能定位到行 |
| 结束必须自动校验 | "跑完了"不等于"跑对了"，数量对不上就是失败 |

### 4.2 五步，每步都有产物

所有命令在项目目录下用 PowerShell 执行（本机是 5.1，没有 pwsh 7）：

```powershell
# 1. 生成输入数据（内置行业词表 + 句型模板 + 固定种子）
powershell -NoProfile -ExecutionPolicy Bypass -File .\tools\gen-data.ps1
# 2. CSV → DXL
powershell -NoProfile -ExecutionPolicy Bypass -File .\tools\csv2dxl.ps1
# 3. 导入 DOORS（COM 调用运行中的客户端）
powershell -NoProfile -ExecutionPolicy Bypass -File ..\doors\doors-run.ps1 `
  -DxlFile .\dxl\import-all.dxl -WaitSeconds 900
# 4. 自动校验（逐模块读回比对数量）
powershell -NoProfile -ExecutionPolicy Bypass -File .\tools\verify.ps1
# 5. 链接与覆盖报告
powershell -NoProfile -ExecutionPolicy Bypass -File .\tools\link-report.ps1
```

| 步骤 | 产物 | 耗时 |
|---|---|---|
| 生成数据 | `data/requirements.csv`（767 行） | < 1 秒 |
| 转 DXL | `dxl/import-all.dxl`（1691 行） | < 1 秒 |
| 导入 | 5 个文件夹 + 7 个模块 + 767 个对象 | **约 12 秒** |
| 校验 | `output/verify-report.txt` | 数秒 |
| 建链 | `output/link-report.txt` | 约 15 分钟（662 条） |

### 4.3 校验日志长什么样

```
import start
folder 01 系统需求: exists
folder 02 子系统需求: created
SYS: created (97 reqs, 24 headings)
SEC: created (90 reqs, 23 headings)
import done
```

这段日志是整条链路里最值钱的东西：它让"导入成功"变成一个**可验证的事实**，而不是一句口头承诺。

### 4.4 为什么用 COM 而不是 CLI

DOORS 9.6 没有官方命令行导入接口。可行的路径只有两条：GUI 手工导入，或者通过 COM 驱动运行中的客户端执行 DXL。前者不可重复，后者可以脚本化——代价是**必须有一个已登录的 DOORS 客户端在跑**。

![DOORS 数据库目录](/docs/doors/screenshots/db-tree.png)

*导入后的库结构：需求、用例、代码、变更单各自成模块，按项目文件夹分组。*

## 五、数据设计：CSV 的 14 个字段

链路能不能跑通，八成取决于这张表设计得对不对。

### 5.1 字段定义

| 字段 | 说明 | 示例 |
|---|---|---|
| Module | 模块代号 | `SEC` |
| ModuleName | 模块名（也是库里的模块名） | `SEC_安防子系统需求` |
| Folder | 所属项目文件夹 | `02 子系统需求` |
| Kind | 行类型：`章节` / `小节` / `需求` | `需求` |
| Chapter | 所属章节 | `3.2 远程开门` |
| ReqId | 需求编号（仅需求行） | `SEC-0042` |
| Title | 需求标题 | `门禁远程开门` |
| Type | 功能 / 性能 / 安全 / 接口 / 可靠性 | `功能` |
| Desc | 需求正文 | `系统应支持门禁远程开门，权限下发在 10 秒内生效。` |
| Priority | 高 / 中 / 低 | `高` |
| Method | 验证方法：测试 / 演示 / 分析 / 检查 | `测试` |
| Status | 已评审 / 待评审 / 草稿 | `已评审` |
| Owner | 责任人 | `张伟` |
| Source | 需求来源 | `客户需求` |

### 5.2 一个必须做的取舍：属性还是正文

DOORS 9.6 里用 DXL 动态创建自定义属性（AttrDef）比较麻烦。我们的选择是：**把元数据内嵌在需求正文里**。

导入后的 `Object Text` 长这样：

```
SEC-0042 门禁远程开门：系统应支持门禁远程开门，权限下发在 10 秒内生效。
【类型:功能｜优先级:高｜验证:测试｜状态:已评审｜责任人:张伟｜来源:客户需求】
```

**好处**：不依赖模块模板，任何空库都能导。
**代价**：不能按属性筛选，只能全文搜索。

如果企业强制要求"属性列"，正确做法是：先在 GUI 里给模板模块定义好属性，再用 DXL 按属性名赋值（`o."优先级" = "高"`）。这条路我们没走，因为试点阶段"能跑通"比"字段漂亮"更重要。

## 六、追溯：怎么连，覆盖率怎么算才可信

链接是这套东西的核心。没有链接，DOORS 只是一个更贵的 Excel。

![F02 追溯链与覆盖率](/docs/doors/figures/F02-追溯与覆盖率.png)

*图 F02 · 四层链路：URD → SRS → SDD → TC，断链会被单独列出回补。*

### 6.1 链接怎么建

| 方式 | 效率 | 适用 |
|---|---|---|
| 拖拽 / Link 菜单 | 低 | 少量、临时补充 |
| 链接模块里逐条点选 | 中 | 评审后集中补链 |
| DXL 批量建链 | 高 | 一次性从 Excel 导入关系 |

662 条链接是脚本建的，分三批：基础链 475 条约 4.5 分钟，补 120 条约 15 分钟，最后一次全量重建。**建链比建对象慢两个数量级**，这是很多人没预料到的。

### 6.2 覆盖率的分母最容易出错

一个团队跟我说"我们覆盖率 92%"，我问了三个问题，数字就崩了：

1. **分母里有没有章节标题？** 有——那 162 个标题会把分母撑大。
2. **废弃需求算不算？** 算——那分子永远追不上。
3. **按哪个时点统计？** 说不清——那这个数字下周就不可比。

正确的口径必须写清四件事：

| 要素 | 我们的定义 |
|---|---|
| 分母 | 仅 `Object Text` 类型、状态为「已评审」的对象 |
| 分子 | 至少有一条 out-link 指向测试用例的需求 |
| 排除 | 章节标题、废弃需求、占位行 |
| 时点 | 基于某次基线快照统计 |

![追溯矩阵](/docs/doors/screenshots/matrix.png)

*矩阵视图：横轴测试用例、纵轴系统需求，空白格就是没覆盖的地方。*

> 覆盖率不是越高越好。100% 覆盖通常意味着用例和需求一一对应，反而牺牲了异常路径。

### 6.3 三类断链要分开看

| 类型 | 定义 | 处理 |
|---|---|---|
| 孤儿需求 | 没有 out-link 的需求 | 补测试用例 |
| 孤儿用例 | 没有 in-link 的用例 | 补需求或标记为探索性测试 |
| 断链 | 目标对象已删除 | 清理链接，避免统计污染 |

## 七、变更：基线怎么用

基线的意义不是"备份"，是**给变更一个可比较的参照物**。

![F03 基线与变更影响](/docs/doors/figures/F03-基线与变更.png)

*图 F03 · 改动前后各打一个基线，差异清单只是起点，影响面要顺着链接找下游。*

### 7.1 原生基线的六个动作

| 步骤 | 操作 | 说明 |
|---|---|---|
| 1 | 建「基线集定义」 | 定义这一组基线包含哪些模块 |
| 2 | 把模块加入定义 | 一次加入，后续沿用 |
| 3 | 建「基线集」（版本） | 一次基线集 = 一个版本快照 |
| 4 | 给模块打第一个基线 | 评审通过后立即打 |
| 5 | 改需求，再打第二个基线 | 变更后重新评审、重新打 |
| 6 | 比较两个基线 | 看 redline 视图，导出差异清单 |

### 7.2 差异 ≠ 影响面

这是产品上最容易被混淆的一组概念：

| 概念 | 含义 | 怎么得到 |
|---|---|---|
| 差异 | 哪些对象的内容变了 | 比较两个基线 |
| 影响面 | 哪些下游交付物需要跟着改 | 差异对象 + 链接可达的下游集合 |

只做差异，团队会漏改测试；做到影响面，才知道"这次改动要通知谁、要重跑哪些用例"。我们的做法是先导差异清单，再用 DXL 顺着 out-link 展开两层，得到受影响用例列表。

## 八、16 个阶段里，工具能管到哪

DOORS 不是万能的。把需求工程的 16 个阶段摊开看，它的能力边界其实很清楚。

| # | 阶段 | 核心问题 | 主责工具 |
|---|---|---|---|
| 1 | 需求获取 | 谁、在什么场景、想要什么 | Jira / Confluence |
| 2 | 需求分析 | 哪些做、先做哪个、冲突怎么解 | Jira |
| 3 | 需求规格化 | 怎么写成可验证、可追溯的需求 | **DOORS** |
| 4 | 需求评审 | 有没有错、漏、歧义 | **DOORS 讨论** |
| 5 | 需求基线 | 什么时候冻结，冻结哪一版 | **DOORS 基线** |
| 6 | 架构设计 | 系统由哪些部分组成 | EA / Rhapsody |
| 7 | 详细设计 | 模块内部怎么实现 | EA / OpenAPI |
| 8 | 需求分配 | 每条需求由谁实现 | **DOORS 链接** |
| 9 | 编码实现 | 把需求写成代码 | Git / GitLab |
| 10 | 单元测试 | 函数和类是否正确 | JUnit / pytest |
| 11 | 集成测试 | 模块之间能不能通 | Postman / JMeter |
| 12 | 系统测试 | 端到端是否符合系统需求 | TestRail / Xray |
| 13 | 验收测试 | 业务是否接受 | TestRail / 客户环境 |
| 14 | 发布上线 | 何时、发多少、怎么回滚 | Jenkins + Argo CD |
| 15 | 变更控制 | 改不改、影响谁、谁批 | **DOORS 变更单** |
| 16 | 追溯与度量 | 每条需求能否追到底 | **DOORS + BI** |


### 8.1 每个阶段在干什么、边界在哪

| # | 阶段 | 在干什么 | 工具边界 |
|---|---|---|---|
| 1 | 需求获取 | 问清谁在用、什么场景、要什么 | 工具只记录想法，不判断冲突 |
| 2 | 需求分析 | 做减法：200 条收敛到 80 条 | 优先级是资源分配，工具只存结果 |
| 3 | 需求规格化 | 翻译成可验证、可追溯的句子 | 强在关系与版本，弱在表达与计算 |
| 4 | 需求评审 | 让三种理解撞一次 | 工具留意见，不判对错 |
| 5 | 需求基线 | 冻结之后能对比 | 做不了分支合并，只有一条主线 |
| 6 | 架构设计 | 把需求翻译成可分工的单元 | 模型是快照，不随需求自动更新 |
| 7 | 详细设计 | 模块内部怎么实现 | 不校验是否覆盖全部需求 |
| 8 | 需求分配 | 需求与人/组件的对应矩阵 | 工具存关系，完整性靠查询 |
| 9 | 编码实现 | 需求要能追得回代码 | 版本工具不懂需求，除非提交里写编号 |
| 10 | 单元测试 | 自检与回归保护 | 覆盖率≠逻辑正确 |
| 11 | 集成测试 | 模块拼起来还能不能跑 | 验证契约，结论受环境影响 |
| 12 | 系统测试 | 端到端 + 非功能指标 | 证明测过的没问题，不证明没测的 |
| 13 | 验收测试 | 业务方用自己的场景判定 | 工具留证，人签字 |
| 14 | 发布上线 | 可重复、可回滚、可观测 | 发布链不知道需求的存在 |
| 15 | 变更控制 | 变了什么、影响谁、谁批 | 需求工具做不了审批流，审批流不懂依赖 |
| 16 | 追溯与度量 | 把网串起来，把状态变成数字 | 链接是人建的，指标靠各系统导出 |


### 8.2 一条需求的完整旅程

抽象讲阶段没感觉，跟着一条需求走一遍就清楚了。

**第 1 天 · 获取。** 业务方说"访客要能刷脸进园区"。这句话是素材，不是需求：谁审批访客、几点到几点有效、刷脸失败怎么办，都没说。

**第 3 天 · 规格化。** 落成 `UR-0007 访客刷脸入园：访客经被访人确认后，可在预约时段内刷脸入园，失败时前台可人工放行。` 一句话，三个可验证点。

**第 5 天 · 评审。** 安保提出"夜间不允许访客入园"，这条被拆成一条独立的系统需求 `SYS-0031`，而不是塞进原来的句子里。评审的价值就在这里：把隐含假设逼出来。

**第 2 周 · 分配与设计。** `SYS-0031` 分解到 `SEC`（安防子系统）下的三条软件需求，分别对应门禁控制器、人脸服务、消息推送。

**第 3 周 · 测试。** 三条软件需求各挂 1–2 个测试用例，共 4 个。矩阵视图上，`UR-0007` 这一行终于有了实心点。

**第 6 周 · 基线。** 评审通过，打基线 v1。此时 `UR-0007` 的完整链路是：1 条用户需求 → 1 条系统需求 → 3 条软件需求 → 4 个用例。

**第 3 个月 · 变更。** 业务方要求"访客可以带同行人"。改 `UR-0007` 一句话，影响面是：`SYS-0031` 要改、3 条软件需求里 2 条要改、4 个用例里 3 个要重跑。

**如果没有链接会怎样**：只能靠人回忆"这个改动还影响哪儿"，漏掉的那两个用例，会在上线后变成线上问题。

> 这条链路就是这套系统存在的全部理由——不是为了存档，是为了**改动时能算出影响面**。

闭环是：**定义（1-5）→ 设计（6-8）→ 实现（9）→ 验证（10-13）→ 交付（14）→ 治理（15-16）**。

DOORS 出现在 8 个阶段里，但真正"只有它能做"的只有三个：规格化（对象化）、基线（快照）、追溯（链接）。

一句话：**DOORS 保证"可追溯"，但不保证"正确"。** 需求写得对不对、测试设计得好不好、变更该不该批，都是人的判断。

## 九、十个坑

这部分是实操记录，写下来是为了让下一个人少走一遍。

| # | 坑 | 现象 | 解法 |
|---|---|---|---|
| 1 | 中文编码三套并存 | CSV、DXL、DOORS 编码不一致，导进去是乱码 | 全链路统一 UTF-8，DXL 写 BOM |
| 2 | `create()` 是相对路径 | 以为建在根目录，实际建在当前文件夹 | 先 `cd` 到目标文件夹再建 |
| 3 | 新对象插到顶部 | 导入后顺序全反了 | 倒序插入，或导入后重排 |
| 4 | 重复导入报错 | 第二次跑直接抛异常 | 导入前查重，脚本做成幂等 |
| 5 | DXL 语法怪癖 | 字符串转义、括号匹配与常规语言不同 | 小批量试跑，看错误行号 |
| 6 | 报错弹模态框卡死 | 无人值守时整个 COM 调用挂住 | 执行器里加弹窗自动关闭 |
| 7 | 路径要用正斜杠 | Windows 反斜杠在 DXL 里被吃掉 | 统一 `/` |
| 8 | 模块不能建在根目录 | 直接建报权限/路径错 | 先建项目文件夹 |
| 9 | 校验只看总数 | 总数对但模块错位 | 逐模块比对数量 |
| 10 | 没写回滚 | 导错了只能手工删 | 每步留快照，支持重来 |

### 补充：三个看起来不严重、实际最耗时的坑

- **弹窗卡死**：DXL 执行报错会弹模态框，无人值守时整个流程挂住。解决方式是执行器里轮询窗口并自动点掉。
- **中文乱码**：不是"都是 UTF-8 就行"，而是 CSV、DXL 文件、DOORS 客户端三者都要在同一编码下，缺一个就乱。
- **链接比对象慢**：建 995 个对象 12 秒，建 662 条链接 15 分钟。批量建链前一定要先小批量验证规则。

## 十、常见问题（FAQ）

| 问题 | 现象 | 处理 |
|---|---|---|
| 导入后中文是乱码 | 属性值显示 `??` 或方块 | 检查 CSV 与 DXL 是否都带 BOM，DOORS 语言包是否装 |
| 第二次导入失败 | 模块已存在，`create()` 报错 | 脚本加存在性判断，或换库重跑 |
| 链接建不上 | 提示目标对象不存在 | 确认 ReqId 在目标模块里唯一 |
| 校验数量对不上 | 差几个对象 | 多半是章节行被当成需求行，看 `Kind` 列 |
| 基线比较看不到差异 | 比较的是同一版本 | 确认选的是两个不同基线集 |

## 十一、换成真实业务数据怎么做

这套脚本不是只能跑演示数据。换成真业务，三步：

| 步骤 | 做什么 | 注意 |
|---|---|---|
| 1 | 只换数据 | 按 14 个字段填 `requirements.csv`，先跑 1 个模块验证 |
| 2 | 加字段 | 在 CSV 加列，同步改 `csv2dxl.ps1` 的字段映射 |
| 3 | 要属性列 | 先在 GUI 给模板模块定义属性，再改 DXL 按属性名赋值 |

建议顺序是：**先跑通一个模块 → 再放全量 → 最后动属性列**。反过来的话，属性定义一旦出错，全量数据都要重导。

## 十二、什么情况下不要用 DOORS

这是产品经理最该回答、但最少被写出来的问题。

| 信号 | 建议 |
|---|---|
| 需求 < 100 条，团队 < 5 人 | 用 Markdown + Git，更轻也够用 |
| 没有外部合规/审计要求 | 不必上重工具，先把流程跑顺 |
| 设计和测试不参与 | 别上——链接永远建不起来，覆盖率是假的 |
| 没有人愿意当"需求库管理员" | 别上——工具需要有人维护结构和口径 |
| 只是想"把文档存起来" | 用网盘或 Wiki，DOORS 解决不了"存"的问题 |

## 十三、如果重来一次

| 教训 | 下次怎么做 |
|---|---|
| 先定口径，再跑数据 | 覆盖率、状态、层级定义先写成一页纸，全员确认 |
| 先做小批量闭环 | 先导 1 个模块跑通"导入 → 校验 → 出报告"，再放全量 |
| 链接和需求同时进 | 需求导完立刻建链，别等"以后补"——以后永远不会来 |
| 把校验做成门禁 | 数量不符直接 fail，不给人"先跑通再修"的侥幸 |
| 培训四类人，不只培训需求工程师 | 设计不建链、测试不挂用例，这套东西就是个文档库 |

---

**一句话总结**：DOORS 不是一个更好的文档工具，而是一套把需求变成可追溯对象的协作基础设施。工具只占三成，数据规范、口径共识、以及四类人一起维护，占七成。
